# Assurance case

This page argues that PQ-Proof meets the security requirements below, within the limits listed under Residual risks. It states the threat model and the trust boundaries, shows which secure design principles the code follows, and lists the common implementation weaknesses it counters. [DESIGN.md](DESIGN.md) is the specification and [SECURITY.md](SECURITY.md) explains how to report a problem. Code links point to commit `1e9aa5b`, so the line numbers stay valid when the code moves on.

## Scope and security requirements

PQ-Proof reads an original and a converted tree (or one tree in check mode), judges the migration by fixed rules, and writes an evidence folder. `pqproof impl judge` compares KAT answers with pinned reference versions. Two optional steps reach outside the inputs. The first is `TLS_TARGETS`, which measures running servers with `tls_probe`. On the host with OpenSSL 3.5 or later it also measures them with `openssl s_client` ([prove.py L538](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L538), [prove.py L564-L566](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L564-L566)). The second is `--pq-verify`, which runs pq-verify on a library.

The requirements below restate the list of security problems in [SECURITY.md](SECURITY.md#what-counts).

1. Verdict integrity. A tree that the documented rules fail does not get a pass. A check that did not run is never counted as passed.
2. Evidence integrity. `--verify` rejects an evidence folder in which a file was changed, added or removed, apart from the limit stated under Residual risks.
3. Host safety. An input tree, zip, answer file, `.rsp` or evidence folder cannot make PQ-Proof run code from it, write outside its output folder, or read files outside the inputs.
4. Bounded external programs. Python starts each external program from an argument list, never from a shell command string. Inside `scan/cbom-scan.sh`, bash runs `openssl` and `keytool`. Each call runs under a time limit, except the two local reference servers, which the run stops when it ends. Options that fetch vectors from the network, swap the vector folder, write files, hide failures in the exit code, run a harness or compile source are refused ([impl.py L1127-L1138](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/impl.py#L1127-L1138)).
5. Release integrity. A user can check that a release file was built by this repository's release workflow.

Each requirement rests on the arguments below and is limited by the residual risks.

| Requirement | Supported by | Limited by |
|---|---|---|
| 1. Verdict integrity | Fail-safe defaults, Separation of privilege, CWE-436 | the allowlist, static detection gaps, the server that was measured, a replaced `tls_probe` |
| 2. Evidence integrity | Complete mediation, Open design, CWE-354, CWE-436, CWE-59 | a folder rewritten with every hash recomputed, the `lstat` window on Windows |
| 3. Host safety | Least privilege, Economy of mechanism, CWE-22, CWE-59, CWE-78, CWE-427, CWE-79, CWE-400 (size) | pq-verify loads the library it checks, parser bugs in `openssl` and `keytool` |
| 4. Bounded external programs | Least privilege, CWE-78, CWE-400 (time) | a timeout kills only `bash`, not the programs the script started |
| 5. Release integrity | CWE-494 | release checks work only when users run them, a local substitution (A5) |

Out of scope: whether the rules are right or complete ([DESIGN.md](DESIGN.md#limits)), what a library does when pq-verify loads it ([SECURITY.md](SECURITY.md#what-counts)), and the security of the servers that PQ-Proof measures.

## Threat model

Assets:

- the verdict, the check statuses and everything derived from them (exit code, SARIF, GitHub Action outputs);
- the evidence folder: `receipt.json`, its `receipt_id` and every file it lists;
- the host that runs the tool, including CI runners and their tokens;
- the release files: wheel, sdist, `tls_probe` binaries, `SHA256SUMS` and `BUILDINFO`.

Attackers:

- A1, the author or agent that produced the converted tree. A1 wants a pass for an unfinished migration and controls every file, name, link and allowlist entry in that tree, including the review fields.
- A2, someone who edits an evidence folder after the run to change the verdict or hide a finding.
- A3, someone who hands PQ-Proof a crafted zip, answer file, `.rsp` or evidence folder. A3 wants code execution, a write outside the output folder, a crash or a hang.
- A4, a malicious or intercepted TLS server named in `TLS_TARGETS`. A4 wants a hybrid result it did not earn, or wants to inject lines into the probe output.
- A5, someone who can replace a local program the tool runs, such as the `tls_probe` binary, `openssl` or pq-verify.
- A6, someone who tampers with a release on its way to the user, or with the CI pipeline that builds it.

The person who runs the tool and sets its environment is trusted. A5 needs write access to the host, so the tool cannot stop A5. It records the path, version and SHA-256 of OpenSSL, `tls_probe` and pq-verify, so a reader can spot a substitution of those three ([prove.py L1092-L1103](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1092-L1103), [prove.py L1511-L1512](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1511-L1512)).

`openssl` and `keytool` parse key, certificate and keystore files from the input tree inside `scan/cbom-scan.sh`. Their parsers sit on the boundary. The tool limits the time the whole scan may take to 900 s ([prove.py L431-L435](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L431-L435)). On a timeout only the bash process is killed. Programs the script started may keep running. Keystore password candidates pass through an environment variable, so they stay out of the process list ([cbom-scan.sh L676-L677](https://github.com/g1mn/pqproof/blob/1e9aa5b/scan/cbom-scan.sh#L676-L677), [cbom-scan.sh L693-L694](https://github.com/g1mn/pqproof/blob/1e9aa5b/scan/cbom-scan.sh#L693-L694)).

## Secure design principles

Fail-safe defaults. A check ends as pass, fail, needs review, undecided or not applicable, and only pass counts as passed ([DESIGN.md](DESIGN.md#skipped-is-not-passed)). Three cases leave the check undecided: a scanner that did not finish ([rules.py L793](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/rules.py#L793), [rules.py L916](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/rules.py#L916)), a TLS server in the code with no `TLS_TARGETS` ([rules.py L882-L884](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/rules.py#L882-L884)), and a pq-verify that cannot be found ([prove.py L1508-L1509](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1508-L1509), [impl.py L1269-L1270](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/impl.py#L1269-L1270), [impl.py L1341-L1342](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/impl.py#L1341-L1342)). Any undecided check makes the verdict undecided ([receipt.py L542-L548](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/receipt.py#L542-L548)), with exit 3 ([prove.py L1205](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1205)). A zip that could unpack differently on another machine is an input error ([prove.py L257-L289](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L257-L289)), with exit 2 ([prove.py L2164-L2166](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L2164-L2166)). The tests follow the same rule: with `STRICT=1` a skipped test fails the CI run ([ci.yml L127-L137](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/ci.yml#L127-L137), [run_unit.py L43-L44](https://github.com/g1mn/pqproof/blob/1e9aa5b/tests/run_unit.py#L43-L44)).

Complete mediation. A run writes the evidence and then runs the same verification as `--verify` on the folder it just wrote ([prove.py L1165](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1165), and for `impl judge` [prove.py L1682](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1682)). `--verify` recomputes `receipt_id`, every file hash and the ruleset hash, rejects files the receipt does not list, checks the verdict against the numbers below it, and rebuilds `receipt.html`, `deck.json` and `README.txt` to compare them byte for byte. The full list is under Recheck in [DESIGN.md](DESIGN.md#verification-evidence-and-the-evidence-hash), and the code is [receipt.py L1113-L1230](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/receipt.py#L1113-L1230).

Separation of privilege. Two scanners read the code on purpose. The rows of both go into one table, and a line that either of them blocks counts as blocking, so a zero count needs both to find nothing ([prove.py L909-L912](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L909-L912), [rules.py L464-L467](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/rules.py#L464-L467)). If `cbom-scan.sh` did not finish, the check is undecided instead ([rules.py L793](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/rules.py#L793)).

Least privilege. The code narrows what each external program and CI job can reach in the ways below.

- pq-verify starts through `run_logged`, from an argument list without a shell ([prove.py L1443-L1486](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1443-L1486)). The scanners, `tls_probe`, `docker` and `openssl s_client` start the same way ([prove.py L431-L432](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L431-L432), [prove.py L514-L515](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L514-L515), [tlsprobe.py L198-L202](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/tlsprobe.py#L198-L202), [tlsprobe.py L315-L321](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/tlsprobe.py#L315-L321)).
- The pq-verify argument string must pass an allowlist of options ([impl.py L1121-L1138](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/impl.py#L1121-L1138), [impl.py L1145-L1200](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/impl.py#L1145-L1200)).
- pq-verify runs in an empty temporary folder ([prove.py L1507](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L1507)) with loader and Python path variables removed ([impl.py L1212-L1216](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/impl.py#L1212-L1216)).
- The scanner never gets `HOST_FILES`, so it does not open certificates and host keys outside the tree that a config file points to ([prove.py L422-L423](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L422-L423), [cbom-scan.sh L496-L511](https://github.com/g1mn/pqproof/blob/1e9aa5b/scan/cbom-scan.sh#L496-L511)).
- Container mode starts the probe with `--pull=never` and mounts the binary folder read-only ([tlsprobe.py L254-L258](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/tlsprobe.py#L254-L258)).
- Some steps get more than they need. Container mode runs the probe as root with `--user 0:0` and mounts the TLS folder read-write ([tlsprobe.py L256-L257](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/tlsprobe.py#L256-L257)). Both scanners get the operator's full environment except `HOST_FILES` ([prove.py L422-L423](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L422-L423), [prove.py L509](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L509)).
- CI and release start from a read-only token ([ci.yml L26-L27](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/ci.yml#L26-L27), [release.yml L21-L22](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/release.yml#L21-L22)). At this commit all 14 `actions/checkout` steps in `.github/workflows/` set `persist-credentials: false` (for example [release.yml L105-L107](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/release.yml#L105-L107)). zizmor checks the workflows in CI ([ci.yml L256-L257](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/ci.yml#L256-L257)).
- The GitHub release job is the only job with `contents: write`, next to `id-token: write` and `attestations: write` ([release.yml L197-L203](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/release.yml#L197-L203)).
- The PyPI job gets only `id-token: write`, behind the `pypi` environment ([release.yml L253-L260](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/release.yml#L253-L260)). The workflow uses no PyPI API token.
- The CodeQL job gets `security-events: write` ([codeql.yml L19-L22](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/codeql.yml#L19-L22)). The Scorecard job gets `security-events: write`, `id-token: write` and `actions: read` ([scorecard.yml L20-L24](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/scorecard.yml#L20-L24)). The Pages workflow sets `pages: write` and `id-token: write` at workflow level, for its one deploy job ([pages.yml L11-L14](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/pages.yml#L11-L14)).
- The ClusterFuzzLite workflow starts from no permissions, and its job gets `contents: read` ([cflite.yml L10](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/cflite.yml#L10), [cflite.yml L18-L19](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/cflite.yml#L18-L19)). `code-mutants.yml` and `kpqc-e2e.yml` get `contents: read` ([code-mutants.yml L11-L12](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/code-mutants.yml#L11-L12), [kpqc-e2e.yml L18-L19](https://github.com/g1mn/pqproof/blob/1e9aa5b/.github/workflows/kpqc-e2e.yml#L18-L19)).

Economy of mechanism. The Python code has no runtime dependencies ([pyproject.toml L41](https://github.com/g1mn/pqproof/blob/1e9aa5b/pyproject.toml#L41)) and uses only the standard library. The rest of the trusted base is the shell scanners and the external programs listed under Trust boundaries. `tls_probe` imports only Go standard packages ([tls_probe.go L26-L52](https://github.com/g1mn/pqproof/blob/1e9aa5b/probe/tls_probe.go#L26-L52)) and is built with `CGO_ENABLED=0 GOPROXY=off` ([build-probe.sh L15](https://github.com/g1mn/pqproof/blob/1e9aa5b/build-probe.sh#L15)). Python starts with `-I` (isolated mode) and `-B` (no bytecode files), so a file in the input tree or the working folder cannot shadow a module ([prove.sh L60-L81](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.sh#L60-L81), [prove.py L38-L40](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L38-L40)).

Open design. The rules, the ruleset hash, the tree hash and the evidence hash (RFC 8785 and SHA-256) are documented, and anyone can recompute them. A second implementation in `src/pqproof/sarif.py` ([sarif.py L201-L203](https://github.com/g1mn/pqproof/blob/1e9aa5b/src/pqproof/sarif.py#L201-L203)) recomputes every golden receipt in `tests/test_evidence_strict.py` ([test_evidence_strict.py L131-L136](https://github.com/g1mn/pqproof/blob/1e9aa5b/tests/test_evidence_strict.py#L131-L136)). A short JavaScript version inside the same test does it again when Node.js is installed ([test_evidence_strict.py L139-L161](https://github.com/g1mn/pqproof/blob/1e9aa5b/tests/test_evidence_strict.py#L139-L161)).

## Reproducibility

The scanners do not open files outside the tree that the tree points to. `HOST_FILES` is removed and links are not followed ([prove.py L422-L423](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L422-L423), [cbom-scan.sh L496-L511](https://github.com/g1mn/pqproof/blob/1e9aa5b/scan/cbom-scan.sh#L496-L511)). The tool refuses zip names that differ only in case or Unicode normalization, and refuses control characters in file names ([prove.py L262-L275](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L262-L275), [prove.py L373-L375](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L373-L375)). With the same tool versions and the settings recorded in `params`, a run on one machine gives the same verdict on another.

## Residual risks

- Anyone who can rewrite an evidence folder can change any file and recompute every hash and `receipt_id` at once. `--verify` then passes. A hash shows that a file is the one the evidence describes, and it says nothing about who wrote it. Compare `receipt_id` with a value from a place you trust, such as the console output of the run, a CI log or a ticket that records it ([DESIGN.md](DESIGN.md#verification-evidence-and-the-evidence-hash)).
- A TLS target given without a CA file is trusted on first use. The probe takes the last certificate of the chain from a first, unverified connection and verifies the second connection against it ([tls_probe.go L237-L267](https://github.com/g1mn/pqproof/blob/1e9aa5b/probe/tls_probe.go#L237-L267), [tls_probe.go L304-L315](https://github.com/g1mn/pqproof/blob/1e9aa5b/probe/tls_probe.go#L304-L315)). Whoever answers that first connection decides the trust anchor. The evidence records `trust` as `tofu` for such a target ([prove.py L561](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L561)). Pass `#/path/ca.pem` to avoid this ([guide/configuration.md](guide/configuration.md#tls-targets)).
- A replaced `tls_probe` binary could report any result. The tool compares its hash with the release list and records `release`, `local` or `unchecked`. That label is only added to the version string and does not change the verdict. A source checkout always says `unchecked` ([tlsprobe.py L128-L152](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/tlsprobe.py#L128-L152), [prove.py L601-L602](https://github.com/g1mn/pqproof/blob/1e9aa5b/prove.py#L601-L602)). The same holds for `openssl` and pq-verify: the tool records their path, version and SHA-256 and trusts the result. `keytool`, `bash` and `docker` are not recorded.
- The tool cannot tell whether the server it measured runs the converted tree ([DESIGN.md](DESIGN.md#limits)).
- The allowlist changes the verdict. An agent that writes the allowlist can also fill the review fields and compute the digest. The review step has to stay with a person, with `REQUIRE_REVIEW=1` ([DESIGN.md](DESIGN.md#limits)).
- `openssl` and `keytool` parse key and keystore files from the input tree. A parser bug in those programs is outside PQ-Proof. The scan time limit stops PQ-Proof from waiting on a hang. It does not stop the programs the script started, and it does not contain a memory corruption.
- pq-verify loads and runs the library it checks and is no sandbox. Check untrusted libraries in a container or VM ([SECURITY.md](SECURITY.md#what-counts), [guide/impl.md](guide/impl.md#limits)).
- On platforms without `O_NOFOLLOW` and `dir_fd` (Windows), `--verify` checks each path part with `lstat` before opening it. A link swapped in between those two steps is not caught ([receipt.py L362-L371](https://github.com/g1mn/pqproof/blob/1e9aa5b/pqlite/receipt.py#L362-L371)).
- A pass means the rules found nothing. Detection is static and has the gaps listed in [DESIGN.md](DESIGN.md#limits).
- Release checks work only when users run them: `shasum -a 256 -c SHA256SUMS` for the probe binaries and `gh attestation verify <file> --repo g1mn/pqproof` for any release asset ([DESIGN.md](DESIGN.md#versioning-and-maintenance)).

## Keeping this document current

Update this page in the same commit as any of these changes:

- a new input the tool reads, or a new place where it writes;
- a new external program, a new subprocess call or a change to the pq-verify option lists;
- a change to a size limit or a time limit;
- a change to the evidence format or to what `--verify` checks;
- a new workflow, or a change to workflow permissions or to the release steps.

Code links name a commit. When a change moves the lines a row depends on, point the link at the new commit and read the lines again. Before each MINOR release, read the Countered weaknesses table against the code and remove any claim the code no longer supports. `tests/test_docs.py` checks the links of the documents in its `DOCS` list, and it builds those links against `blob/main` ([test_docs.py L12-L15](https://github.com/g1mn/pqproof/blob/1e9aa5b/tests/test_docs.py#L12-L15)). This file is not in that list yet, so its links pinned to a commit are checked by hand, as described above.
