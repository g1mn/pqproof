# Design of PQ-Proof

PQ-Proof takes a codebase before and after a post-quantum migration and checks whether the migration is finished. It looks for classical public-key code left without a recorded reason, checks that ML-KEM and ML-DSA at NIST security category 3 or above are in use (ML-KEM-768 or 1024, ML-DSA-65 or 87; see Algorithm profiles), and checks that no TLS setting got weaker along the way. It calls no AI model and connects only to the TLS servers you list in `TLS_TARGETS` and `TLS_TARGETS_ORIG`, plus its own two reference servers on 127.0.0.1 before it measures them (on macOS, checking a listed server against the system trust store can also reach other addresses for certificate data). It reads the code it inspects and never runs it. The one exception is a tool you turn on yourself: `pqproof impl judge --pq-verify` calls pq-verify, a separate program you install, and pq-verify loads and runs the library it audits. `pqproof doctor` also asks a pq-verify it finds on `PATH` (or `PQ_VERIFY`) for its version with `pq-verify --version`; that call loads no library. Each run leaves verification evidence: the raw tool output, a CBOM for both versions, and an evidence hash that anyone can recompute.

It started as the completion check at the end of my migration pipeline in the finals of a 2026 post-quantum hackathon. [HISTORY.md](HISTORY.md) tells that story and lists what changed after the finals. This is a participant's own tool; the organizers have not reviewed or endorsed it.

Some parts come from an earlier hackathon version of PQ-Proof (`g1mn/pq-proof` at commit `7b7803f`, MIT). Those files say so in their first line.

This page is the specification: what one run decides, the rules behind each check, how the verification evidence and its evidence hash are built, and what the tool cannot tell you. The code is the reference: `pqlite/rules.py` for the checks and allow rules, `pqlite/allowlist.py` for the allowlist, `pqlite/receipt.py` for the evidence. How to install, configure and read the results is in [guide/](guide/): [quick start](guide/quickstart.md), [configuration](guide/configuration.md), [allowlist](guide/allowlist.md), [outputs](guide/outputs.md), [CI](guide/ci.md) and the [implementation check](guide/impl.md). The [site](https://g1mn.github.io/pqproof/) has the overview, the public test results and the KISA mapping. [CHANGELOG.md](CHANGELOG.md) lists releases and their verdict impact.

## One run

```
bash prove.sh <original folder|zip> <fixed folder|zip>
```

1. **Prepare.** Unpack zip inputs, hash both trees, load the allowlist and the data exclusions.
2. **(a) CBOM.** Run `scan/cbom-scan.sh` and `pqlite/scan.py` on both trees and merge their rows by `path:line`. Since ruleset 10 `pkname()` in `cbom-scan.sh` names the SLH-DSA parameter set from its OID (2.16.840.1.101.3.4.3.20 to .31: SHA2 and SHAKE, 128/192/256, s and f). It matters only where OpenSSL prints the raw OID instead of the name: OpenSSL before 3.5 and LibreSSL do that in `x509 -text`, and neither can read an SLH-DSA key with `pkey -text`, so `pkname` is the only place the algorithm gets named. A row read that way used to be plain `SLH-DSA` and counted as safe (category 3 or above); an SLH-DSA-128s row now reads `SLH-DSA-SHA2-128s` and blocks as below category 3, the same way an ML-DSA-44 row does.
3. **(c) Classical-line count.** Run `scan/residue.sh` on both trees and read its per-rule counts and line lists. Then resolve the allowlist against the original as well and count, per entry, the classical lines it covers there (see Allow rules).
4. **(b) TLS weakening.** Compare every changed file before and after with `pqlite/verify.py`.
5. **(b) TLS probe.** Only with `TLS_TARGETS`: check the probe against reference servers, then measure each target.
6. **Checks.** Turn the numbers into eight checks and one verdict.
7. **Evidence.** Write `receipt.json`, `receipt.html`, the tables and `deck.json`, then run the same verification as `--verify` on the folder just written.

`bash prove.sh --check <tree>` (`pqproof check`) judges one tree as it is now, with no original: the tree goes in both slots, `params.mode` is `check`, and the checks that compare two trees are "not applicable" (`a-input` keeps only its skipped-folder, link and size findings, `b-weakening` and `r-review` have no change to look at). A code or folder link that points outside the tree leaves `a-input` undecided there too, and fails it under `REQUIRE_REVIEW=1`. Check mode therefore does not catch TLS weakening or a removed verification call; it guards against classical algorithms coming back, and the two-tree run stays the judgment for a pull request. `bash prove.sh --inventory <tree>` (`pqproof inventory`) gives no verdict: it runs the two scanners and `residue.sh` on one tree and writes `inventory.json` (CBOM counts, blocking locations, classical lines per family, PQC name lines, TLS signals, the ruleset) with `tables/cbom.csv` and the raw output.

`bash prove.sh --impl prompt|judge` (`pqproof impl`) checks a KpqC implementation (SMAUG-T, NTRU+, HAETAE, AIMer) against pinned reference KAT versions, without building or running it. `prompt` writes a question sheet from the KAT excerpts in `scan/kat/` (decapsulate, verify a signature and a signature with one changed byte, and optional seed items for a NIST KAT DRBG build). The user's own harness answers it (`examples/impl/kpqc_harness.py` is one), and `judge` compares the answers, or a full PQCgenKAT `.rsp` against the 100 record digests in `scan/kat-kpqc.json`. A version is a candidate when every item from it matches. The run passes when the candidates are versions the profile accepts (`impl_accept` in the `kpqc` profile, the latest version by default), needs review when an old version or a known variant matches or when the answers cannot tell versions apart, fails on no match or when a changed signature is accepted, and is undecided when an answer is missing, the sheet differs or the self-check fails. It is a match with a reference version's KAT, not a conformance test or a certification. The evidence is format 4 with `params.mode` `impl` and two checks, `i-kpqc` and `i-nist`; it keeps the answer, the answer key and the question sheet, and `--verify` judges the copied answer again with its own rules, whatever ruleset wrote the receipt. It trusts the copied answer key only when it is the key its own KAT list builds, or when the receipt's KAT list is recorded in `scan/ruleset.json` and every version in the copy matches its own list, and it checks the accepted versions against its own `kpqc` profile. A receipt it cannot judge again that way does not verify. [guide/impl.md](guide/impl.md) walks through the flow, the result table and the limits.

NIST algorithms go through a bridge instead of a second implementation. `judge --pq-verify "--audit-kem <library> ML-KEM-768"` (also `--audit-dsa`, `--audit-slhdsa`, `--audit-contained`) runs pq-verify on a NIST PQC shared library and puts its result in the same receipt as check `i-nist`; with no answer file the run holds only that check and `i-kpqc` is not applicable. PQ-Proof finds pq-verify through `PQ_VERIFY` or `PATH`, splits the argument string with `shlex` and calls it without a shell, in an empty temporary folder, with `PQV_*`, `LD_*`, `DYLD_*`, `PYTHONPATH`, `PYTHONHOME`, `PYTHONSTARTUP` and `PYTHONINSPECT` removed from the environment, and stops the whole process group after `PQ_VERIFY_TIMEOUT` seconds (1800 by default). It refuses `--live` (network vectors), `--vector-dir`, `--json`, `--sarif`, `--prompt-out`, `--no-fail`, `--audit-harness`, `--audit-source`, other tasks and abbreviated option names, always adds `--require-full-coverage`, and writes the report into the evidence folder with `--json`. `artifacts/impl/pq-verify/log.json` keeps the argv, exit code, stdout and stderr of `pq-verify --version` and of the audit, like the `tls_probe` log. `i-nist` passes on exit 0, status `VERIFIED`, `verified` true, a report schema that fits the audit (major version 1), a report bound to the file PQ-Proof hashed (the target must be a regular file PQ-Proof could hash), a complete scope (`scope.complete`, or for a KEM report, which has no scope field, all nine KEM stages run) and every check passed. It fails on exit 1, `FINDINGS PRESENT` and at least one stage below its total. Everything else is undecided: an input error (exit 2), a `DEGRADED RUN` line, a partial scope, a check that could not run (for example `--constant-time` without valgrind), no executable, a timeout, a broken report or another schema. When only the FIPS 203 input-check stages fail (`ekCheck`, `dkCheck`, `edgeEk`, `edgeDk`), the check still fails and says so: `i-nist` follows the pq-verify verdict, and the standard lets those checks sit outside the API only if the caller does them. A library that leaves them to the caller by design (PQClean ML-KEM-768 clean, for one) therefore fails `i-nist` even when every KAT stage passes. `tools[]` lists the pq-verify executable with its SHA-256 and version only when it was found. That SHA-256 is of the file on `PATH`, which for a pip install is a small launcher script whose bytes depend on the virtual environment path, not of the installed pq-verify package; the version is what `pq-verify --version` prints. What ties the run to tested pq-verify code is installing it pinned by version and wheel hash (`.github/requirements/pq-verify.txt`). `--verify` reads the copied report and run record again and rebuilds the summary, the status and the check row. pq-verify is not a sandbox, so audit an untrusted library in a container or VM.

The inputs are untrusted. The tool reads files and never runs them. zip entries with absolute paths, `..` or backslashes are refused, symlinks inside a zip are recorded by name and not unpacked, and unpacking stops past 1 GiB. A zip that would unpack differently from one machine to the next is an input error (exit 2): the same name twice, two names that differ only in case or Unicode normalization (one file on macOS and Windows), control characters in a name, a file and a folder with the same name, or more than 500,000 entries. A control character (newline, tab) in a file name inside a folder input is an input error too, because the line-based scanners would miss that file. A file over the size limit (`MAX_FILE_MIB`, 1 MiB by default) is skipped whole by `scan.py`, the weakening check and the allowlist check; the grep-based `cbom-scan.sh` and `residue.sh` still read it. Such code and config files are listed in `inputs.*.oversize`, and one in the fixed tree makes `a-input` need review. Folders are skipped by the rules under Skipped folders below. Only `cbom-scan.sh` (grep, awk, openssl) and `residue.sh` (grep, awk) run as subprocesses, plus `tls_probe` and `openssl s_client` for the TLS step, pq-verify when `impl judge --pq-verify` asks for it, and `pq-verify --version` from `pqproof doctor` and before an `impl judge --pq-verify` audit.

## The eight checks

| Check | Fails when | Undecided when |
|---|---|---|
| `a-input` | never | fewer than half of the original's files exist at the same path in the fixed tree; or the original shows no blocking location, no classical code line and no TLS target, so there was nothing to check |

| `a-cbom` | the fixed CBOM has at least one blocking location; or, under `REQUIRE_RESOLVED=1`, key material the scanner could not open or a public-key API whose algorithm name it could not read | `cbom-scan.sh` did not finish cleanly |
| `b-weakening` | a changed file adds a weakening construct or removes a protection | never |
| `b-tls` | a target does not negotiate the profile's hybrid group (`X25519MLKEM768`, or `SecP384r1MLKEM1024` under `cnsa2`) when offered only that group, or the old client (`X25519,P-256`) is accepted under `CLASSIC=deny` or refused under `CLASSIC=allow`, or `EXPECT=cert` and the certificate key is not one the profile accepts (ML-DSA-65 or 87 by default) | the code shows a TLS server but no `TLS_TARGETS` were given; the original had a TLS server and the fixed tree has none; the reference controls failed or the probe binary is not the expected version; a target's certificate did not verify, so the handshake could not be measured, and nothing measured failed; or OpenSSL 3.5 disagrees with the probe |
| `c-classic` | the fixed tree has classical code lines left in the nine families after allowed lines are taken out, any ML-KEM-512 or ML-DSA-44 (below NIST security category 3), or a write inside a `Legacy*.java` file | `residue.sh` did not produce a summary |
| `c-expect` | a requested algorithm has zero code lines (`kem` and `sig` add up the `EXPECT` rules the profile names: ML-KEM-768 or 1024 and ML-DSA-65, 87 or SLH-DSA 192, 256 by default), or `tls`/`cert` was requested and `b-tls` failed or did not apply | the count is missing, or `b-tls` is undecided |
| `r-review` | never | never |
| `r-allow` | `REQUIRE_REVIEW=1`, and an allowlist entry that allows a line or sends one to review has no accepted review record (see Human review below) or is past its `expires_at`, or an entry is unused (see Unused entries below), or a line passes on the name rule alone | never |

Besides pass, fail and undecided, a check can end as "needs review" or "not applicable". "Needs review" does not change the verdict. It shows up in `a-input` (a file that held a blocking location disappeared, a skipped folder holds code, a link points outside the checks, or a code file is over the size limit), `a-cbom` (an allowlisted line sits on a write path, a composite signature, or key material or an algorithm name the scanners could not read) and `c-classic` (an allowlisted write path or a composite signature), `b-tls` (only client-side TLS), `r-review` and `r-allow` (an allowlist entry in use has no review record, or an entry is unused). When the verdict is pass, every place that prints the verdict adds what is left for a person: removed verification calls (`r-review`, from evidence format 2), entries not yet reviewed, write paths left for review inside allowed ranges, and unused entries. The console shows `VERDICT=PASS (2 allowed entries not yet reviewed by a person; 2 write paths in allowed ranges need review; 1 allowlist entry unused in the fixed tree)`, and `report.md`, `receipt.html`, `tables/fragment.html`, `deck.json` (`verdict_text`, `verdict_text_en`) and `evidence-fragment.json` show 통과(허용 2건 사람 확인 전 · 허용 범위 쓰기 경로 2곳 검토 필요 · 안 쓰인 항목 1건). Each part appears only when its count is above zero. From evidence format 3 the line also counts composite signatures and names every other check that needs review (`needs review: a-input, b-tls`), so a pass with a vanished file or client-only TLS no longer looks like a clean pass. A `verify()` reduced to `return true` gives `VERDICT=PASS (2 removed verifications need review)`: the dropped call and the body that only returns success. Before 0.1.0 that pass carried no note.

The verdict is fail if any check fails, otherwise undecided if any check is undecided, otherwise pass. The exit code follows: 0, 1, 3. A failed self-verification of the written evidence also gives 3. With `FAIL_ON_REVIEW=1` a pass with a check that needs review exits 5; the verdict and the evidence stay the same. An unexpected exception inside the tool exits 4 (tool error) with its traceback, so a pipeline can tell a crash from a failed verdict; before 0.2.0 it exited 1.

### Skipped is not passed

A check that did not run is not a check that passed. Every check ends in one of five states: pass, fail, needs review, undecided or not applicable, and only pass counts as passed. When a check cannot run, for example because no TLS address was given or there is no allowlist, the evidence keeps it by name as not applicable or undecided. A pass verdict means that no check failed or stayed undecided. The checks that did not apply are listed and never folded into the pass. After the verdict the console prints how many checks ended in each state, the SARIF file lists those checks under `notCountedAsPass`, and the GitHub Action prints them at the end of the job summary. The tests follow the same rule: the unit tests, the self-test and the mutation runner count skipped cases apart, and with `STRICT=1` (CI) a skipped case fails the run.

### What counts as blocking

A CBOM row blocks when it is a quantum-breakable public-key use (`cbom-scan.sh` threat "쇼어로 깨짐", which means broken by Shor's algorithm, or "보안레벨 3 미만(PQC)", or a `scan.py` row with threat `shor` or `weak-pqc`; a TLS group setting that leaves out hybrid groups is a `shor` row) and none of these apply:

- the line is a comment or sits in a test path (the list in `scan/test-paths.ere`, see Test paths below). `cbom-scan.sh` puts the flag 주석 (comment) or 테스트·예제 (test or example) at the start of the note; a word in the quoted source line further on is not a flag. It reads a leading `#` as a comment only in languages that use it (not `#include` in C or `#[...]` in Rust), `--` only in SQL, Lua and Haskell, and `;` only in ini, assembly and Lisp files. For Go, JavaScript, TypeScript, Python and Java files, `pqlite/rules.py` also reads the line with the language tokenizer of `pqlite/verify.py`: a row whose code part is empty (a comment, a Python docstring) or, for a name-only match, whose classical name sits only in a trailing comment is a comment;
- `SCOPE=kex` and the row is not about key exchange (it is kept as "out of scope");
- an allow rule below covers it.

A composite signature (ML-DSA-65 or ML-DSA-87 bound to RSA, ECDSA, Ed25519 or Ed448 under one key, as the IETF LAMPS draft and BouncyCastle name it, for example `MLDSA65-ECDSA-P256-SHA512`) neither blocks nor passes silently. Both tools read the same name table (`COMPOSITE_NAME` in `pqlite/scan.py`, `RES_COMPOSITE` in `residue.sh`, `COMPRE` in `cbom-scan.sh`), `a-cbom` and `c-classic` both need review, and the locations are listed in `allowlist.composite`. Before ruleset 2, `a-cbom` read such a name as post-quantum and `c-classic` as classical, so the same line passed one check and failed the other. A composite with ML-DSA-44 is below category 3 and blocks.

A PQ/PQ hybrid (from 0.6.0): a post-quantum row whose code line names two post-quantum families of the same kind, such as ML-KEM with SMAUG-T, NTRU+ or HQC, or ML-DSA with SLH-DSA, FN-DSA, HAETAE or AIMer, gets the reason `PQ/PQ 하이브리드` in `tables/cbom-*.csv`, and `a-cbom` counts the locations. The NIS draft guideline recommends PQ/PQ hybrids from 2036. The mark is a name match on one line and does not change the verdict.

A runtime base image whose OpenSSL is too old to offer `X25519MLKEM768` blocks only when something in the tree terminates TLS with the system OpenSSL (nginx, HAProxy, Apache, Python). Otherwise it stays a row to check.

`a-cbom` and `c-classic` look at the same code with different tools on purpose. In testing, `cbom-scan.sh` missed a ternary such as `getInstance(flag ? "RSA" : "EC")` that `residue.sh` caught. The tool reports zero classical lines only when both agree.

### The classical families

`scan/residue.sh` counts code lines for these rules. Comments and docs are counted apart as `comment`, and code lines in test paths as `test`. The first nine rules make up `c-classic`. Comments follow the language: `//` and `/* */` in C-family files (Java, Kotlin, Scala, Groovy, JavaScript, TypeScript including `.jsx` and `.tsx`, Go, C, C++, C#, PHP, Rust, Swift, Dart), `#` anywhere outside quotes in Python, shell, YAML, TOML, Ruby, Terraform, `sshd_config`, `known_hosts` and Dockerfiles, `#` only at the start of a line in properties, ini and env files, and Python docstrings (a triple-quoted string that starts a statement). Since ruleset 2 the names are matched in any case where code writes them in lower case (`ed25519`, `x25519`, `secp384r1`, `ecdsa`, `diffie-hellman`, `ssh-dss`).

| Rule | Matches |
|---|---|
| `G-RSA` | RSA anywhere in code |
| `G-EC` | EC, ECDSA, ECDH, EC key and parameter classes; `EC` alone only as its own word (not `EC2`, `#EC4899`, `0x00EC` or `AWS::EC2`); lower-case `ecdsa` |
| `G-CURVE` | secp*, prime*v1, P-256/384/521, brainpool, EC OIDs, SSH `nistp256`, Nimbus `Curve.P_256`, in any case |
| `G-OAEP-PKCS1` | OAEP, MGF1, PKCS#1, PSource |
| `G-CLASSIC-SIG` | `withRSA`, `withECDSA`, `withDSA`, RSASSA, RSA-PSS |
| `G-JWT-ALG` | RS256/384/512, ES*, PS* |
| `G-EDDSA` | Ed25519, Ed448, EdDSA, Curve25519, and the lower-case forms as their own word (`'ed25519'`, `ssh-ed25519`, `ed25519_dalek`) |
| `G-X25519` | X25519, X448, XDH, ECDH, KeyAgreement, lower-case `x25519`, `x448`, `ecdh` (same line with ML-KEM in any case counts as hybrid, as in `pqlite/rules.py`) |
| `G-DH-DSA` | DiffieHellman, diffie-hellman, `"DH"`, `'dh'`, `"DSA"`, `ssh-dss`, ElGamal, ECIES, KCDSA and EC-KCDSA (any spelling such as `ECKCDSA`, `KISA_KCDSA_sign`, `kcdsaWithSHA1`, and their OIDs; an OID written with commas or spaces, as in a Go `asn1.ObjectIdentifier{...}`, is not caught, the same limit as `G-CURVE`) |
| `G-WEAK-PQC` | ML-KEM-512, ML-DSA-44, Kyber512, Dilithium2 and SLH-DSA 128 (ruleset 4), in any case and with `-`, `_` or nothing between the parts (`ml-kem-512`, `mldsa44`) |
| `LW-legacy-write` | encryption, signing, key generation or file writes inside `Legacy*.java` |
| `E-MLKEM768`, `E-MLKEM1024`, `E-MLDSA65`, `E-MLDSA87` | ML-KEM-768, ML-KEM-1024, ML-DSA-65 and ML-DSA-87 in code outside test paths, in any case and separator |
| `E-SLHDSA` | an SLH-DSA 192 or 256 parameter set from FIPS 205 (`SLH-DSA-SHA2-192s`, `slh_dsa_shake_256f`): the name needs the hash family, so `SPHINCS+` names and SLH-DSA 128 are not counted (ruleset 4) |
| `E-KPQC-KEM`, `E-KPQC-SIG` | the Korean KpqC algorithms SMAUG-T and NTRU+, HAETAE and AIMer (counted only under `PROFILE=kpqc`) |

`G-AES128` is also printed for information. It does not take part in any check.

### Algorithm profiles

`scan/profiles.json` names, per profile, the `EXPECT` rules that count for `EXPECT=kem` and `EXPECT=sig`, the hybrid group `b-tls` offers alone, and the certificate keys `EXPECT=cert` accepts. `PROFILE` picks one, and `receipt.json` records it as `params.profile`. The file is in the ruleset hash.

| Profile | `kem` | `sig` | TLS group | Certificate |
|---|---|---|---|---|
| `nist-cat3` (default) | ML-KEM-768 or ML-KEM-1024 | ML-DSA-65, ML-DSA-87 or SLH-DSA 192, 256 | `X25519MLKEM768` | ML-DSA-65 or 87 |
| `cnsa2` | ML-KEM-1024 | ML-DSA-87 | `SecP384r1MLKEM1024` | ML-DSA-87 |
| `kpqc` | ML-KEM-768, 1024 or SMAUG-T, NTRU+ | ML-DSA-65, 87, SLH-DSA 192, 256 or HAETAE, AIMer | `X25519MLKEM768` | ML-DSA-65 or 87 |

A profile only changes what counts as expected post-quantum use. It never makes a classical line pass, and ML-KEM-512 and ML-DSA-44 block under every profile. `pqlite/scan.py` reads the KpqC names as post-quantum rows with the note that NIST has not approved them. Before ruleset 2, `c-expect` counted only ML-KEM-768 and ML-DSA-65, so a move to category 5 failed.

### Skipped folders

One file, `scan/skip-dirs`, decides which folders no check reads. `pqlite/skipdirs.py` (the tree list behind `tree_sha256`, `pqlite/scan.py`, `prove.py`) and the `skip_dirs` shell function in `residue.sh` and `cbom-scan.sh` all read it, and a sync test runs the three on the same tree. It has two kinds of names:

- `any`: repository metadata, downloaded dependencies, caches and virtual environments: `.git`, `.hg`, `.svn`, `node_modules`, `__pycache__`, `.gradle`, `.idea`, `__MACOSX`, `.venv`, `venv`, `.tox`, `.terraform`. Skipped at any depth, with two limits. Under `src/main/` such a folder is skipped only next to a build file, so `src/main/java/com/bank/venv/` is checked while `src/main/frontend/node_modules/` next to `src/main/frontend/package.json` is skipped. Away from the top of the tree and from a build file (`app/.tox/`), the folder is skipped but counted like an `output` folder.
- `output`: build output and vendored dependencies, `build`, `target`, `dist` and `vendor`. These are skipped only at the top of the tree or next to a build file (`pom.xml`, `build.gradle`, `package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, `composer.json`, `Makefile` and the rest of the list), and never under `src/main/`. So `svc-a/target/` next to `svc-a/pom.xml` is skipped, while `src/main/java/com/bank/vendor/` and `src/main/java/demo/build/` are checked.

The folders a check skips are the folders the tree hash skips, so two trees with the same `tree_sha256` give the scanners the same files. `inputs.*.skipped` lists the `any` names found, every counted folder (each skipped `output` folder, and each `any` folder skipped under `src/main/` or away from its usual place that holds code files) with its file count and code-file count, and every symbolic link. When a counted folder in the fixed tree holds code files, `a-input` needs review. An `any` folder at the top of the tree or next to a build file is skipped without a count, so a planted build file next to such a folder outside `src/main/` hides it; the tree hash and the file list in the evidence still show the build file. Each run copies the list to `artifacts/skip-dirs` (`skip_dirs` in `receipt.json`) and passes the copy to both scanners (`SKIP_DIRS`).

Before ruleset 2 there were four lists. `residue.sh` skipped `vendor` and `node_modules` at any depth and `build`, `target` and `data` at the top, `cbom-scan.sh` and `pqlite/scan.py` skipped `vendor`, `build` and `target` at any depth, and the tree hash skipped `build`, `target`, `.venv` and `venv` at any depth but kept `vendor`. Classical code moved into a package named `vendor` or `build` under `src/main/` passed, and a `.venv` or a nested `target/` could fail a run with files outside the tree hash.

### Test paths

One file, `scan/test-paths.ere`, decides what counts as test or example code. `cbom-scan.sh` (comment flag "테스트·예제"), `residue.sh` (`test` lines), `pqlite/scan.py` (skips Go and Java test files) and the TLS signal check in `pqlite/rules.py` all read it. Its first non-comment line is the test rule and its second is a main-source marker, both POSIX ERE, matched against `/` plus the path inside the tree. When the marker (`/src/main/`) matches, only the part of the path up to the marker's first `/` goes to the test rule. So nothing under `src/main/` is a test path, whatever its package or class name (`com/example/`, `SelfTest.java`), while `tests/it/src/main/` still is. The test rule covers the folders `test`, `tests`, `__tests__`, `__mocks__`, `testdata`, `integrationTest` and `testFixtures` at any depth, the folders `spec`, `fixtures`, `mock(s)`, `example(s)` and `sample(s)` only at the top of the tree, and the file names `*_test.go`, `test_*.py`, `*_test(s).py`, `test(s).py` (Django), `conftest.py`, `*Test.java`, `*Tests.java`, `*Test(s).kt`, `*.test.*`, `*.spec.*`, `*.cy.*` and `*.e2e-spec.*` for JavaScript and TypeScript (with `.jsx` and `.tsx`), `test.js`-style files and `*_spec.rb`. A keystore in a test path carries the test flag like any other key file. Each run copies the file to `artifacts/test-paths.ere`, passes that copy to both scanners (`TEST_PATHS`), and records its hash. A scanner run without the file stops with a usage error. A file with only the first line works as before, with no marker.

Classical code lines in test paths do not count toward `c-classic` or `a-cbom`. `residue.sh` lists them as `TEST` lines, `c-classic` names the first few, and the evidence keeps the count and up to 60 locations (`java.*.tests`; `cbom.*.tests` counts CBOM locations flagged as tests). ML-KEM and ML-DSA lines in test paths do not count for `c-expect`.

The finals version decided this in three places. `cbom-scan.sh` flagged the folder names above at any depth plus the test file names. `pqlite/scan.py`, which feeds the Java and Go rows of `a-cbom`, skipped only Java under `src/test`, `test` or `tests` or named `*Test`, and Go `*_test.go`. `residue.sh` skipped only `src/test`, `test` and `tests`. A negative test in `seal_test.go` therefore passed `a-cbom` and failed `c-classic`. I merged them into one rule. The first merged rule matched every folder name at any depth, and an independent review found that it turned `src/main/java/com/example/`, the default Spring package, into test code: classical Java there passed and a Java-only migration there failed `c-expect`. The main-source marker and the top-of-tree limit for the example-style folders fix that. Skipping more paths risks missing production code kept in a folder named like a test folder. Skipping fewer fails migrations that test the rejection of old keys and pushes test code into the allowlist. The skipped lines stay in the output, so a wide rule costs less than a narrow one. A custom `RESIDUE` script keeps its own test rule unless it reads `TEST_PATHS`.

## Allow rules

A migration often has to keep a few classical lines, for example to read data written before the change. The tool lets a line out of the blocking count only when it can record why. Every allowed line appears in the evidence with its reason, in `receipt.json` under `allowlist` and on the HTML page.

1. **Allowlist** (`ALLOW=<file>`; with an `<W>/orig` input the tool also looks for `<W>/notes/unconverted.json`). Each entry has `where`, `why`, `kind` and an optional `what`.
   - `where` can be `file:line`, `file:start-end`, `file:15,24-40`, a path, or a glob. A bare file name must match exactly one file in the fixed tree. Container paths are resolved against the app root from `recon.json`.
   - An import line counts with an entry when every code line that uses the imported name is allowed. One use elsewhere keeps the import counted. Wildcard imports are never covered.
   - An entry is invalid, allows nothing and leaves a warning when `where` or `why` is empty, the file is missing, the name matches several files, a line range runs past the end of the file, or a glob catches several code files. One bad place invalidates the whole entry, because shifted line numbers should not be trusted.
   - A place the entry itself marks as outside the tree (outside the container or app folder) allows nothing and gives no warning.
   - **Human review.** `reviewed_by` (a name or account) and `reviewed_at` (ISO 8601: `2026-11-18`, `2026-11-18T10:30`, `2026-11-18T10:30:00+09:00`) record who read the reason and when. An entry with either field uses its own pair. A file of the form `{"unconverted": [...]}` can carry one pair at the top for the entries without one. The tool applies that top pair only with a matching `reviewed_digest`: the first 16 hex digits of SHA-256 over the `where`, `what`, `why` and `kind` of the entries it covers (trimmed, as a JSON array with sorted keys and no spaces). The console prints the current value, and `receipt.json` keeps it as `allowlist.top_digest`. Adding or editing an entry, or removing an entry's own pair, changes the value, and every entry under the top pair then counts as not reviewed. An entry's own pair can carry a `reviewed_digest` of that one entry; if present, it has to match. With neither field (or both `null`), the entry is not yet reviewed. An empty or whitespace-only name, a name with control, invisible or bidirectional characters, only one of the two fields, a `reviewed_at` that is not a real date, or a digest that does not match gets a warning and counts as not reviewed. The entry itself stays valid, so a mistake in a review field does not change which lines are allowed. A `reviewed_at` more than a day in the future passes with a warning. The tool counts entries that allow a line or send one to review without an accepted pair in `allowlist.unreviewed`; `r-allow` then needs review, or fails under `REQUIRE_REVIEW=1`. Hybrid and name-rule lines (rules 3 and 4) are not allowlist entries, so they are not counted.

   - **Expiry and approval.** `expires_at` (`YYYY-MM-DD`) and `approval_ref` (a ticket or approval number) are optional. An entry in use whose `expires_at` is before the run date (UTC) counts as expired: it still allows its lines, `allowlist.expired` counts it, and `r-allow` needs review, or fails under `REQUIRE_REVIEW=1`. An entry that expires within 30 days gets a warning. Both fields enter the entry's digest only when they are set, so digests of lists written before 0.2.0 stay the same. `REVIEW_MAX_AGE_DAYS=N` counts a `reviewed_at` older than N days as not reviewed. `--verify` checks `expired` against `started_at`. A field the tool does not read, at the top or in an entry, and a `kind` outside `fallback`, `boundary`, `kept`, `exception`, `false-positive` and `vendored` get a warning; before 0.2.0 an `expires` or `ticket` field was dropped without a word.
     ```json
     {"reviewed_by": "j.kim", "reviewed_at": "2026-11-18T10:30:00+09:00", "reviewed_digest": "f80af1efdb7c95c5",
      "unconverted": [{"where": "Box.java:11-15", "why": "reads records sealed before the migration", "kind": "fallback"}]}
     ```
   - **Unused entries.** A valid entry that covers no classical line in the fixed tree gets status `unused`. The list is written for the fixed tree, but it applies to whatever tree it is run against, so such an entry allows the classical lines in its range when someone runs the list against the original. The tool therefore resolves the same list against the original too (it never judges the original) and records, for every entry, `lines_fixed` (classical lines it covers in the fixed tree, the same lines as `allowed` plus `review`) and `lines_orig` with the locations in `orig`. Each unused entry gets a warning that names the original lines it would cover. `allowlist.unused` and `allowlist.unused_orig_lines` hold the totals, and those original lines count as not reviewed. An unused entry makes `r-allow` need review, or fail under `REQUIRE_REVIEW=1`, whatever its review fields say. An entry that is invalid, excluded or outside the tree in the fixed tree allows nothing there, but it can be valid in the original: an entry for a file the fix deleted, or for lines past the end of a file that got shorter. When such an entry covers classical lines in the original it counts as unused too (its status stays; see `counts_unused` in `pqlite/allowlist.py`), with the same warning, totals and `r-allow` effect. The first version of this fix only warned about it, so a reviewed entry for a deleted file passed under `REQUIRE_REVIEW=1` and still hid the original's lines.
   - **Decision: no automatic blocking.** The tool does not turn those lines back into blocking locations. In one run, the lines an unused entry would hide are in the original, and the original is not judged. If the original goes in the fixed slot, the entry matches lines there and the list holds nothing that says which tree it was written for. So the tool flags the entry where it is unused and leaves deleting it to the person; `REQUIRE_REVIEW=1` enforces that. In a unit test (`tests/test_allowlist.py`, masked case), deleting the unused entry brings the original's blocking locations back. A list without unused entries can still allow the same kept lines in another tree, because those lines exist in both.
2. **Write path.** When an allowed line, or one of the three lines below it within the same function, creates a key, a signature or ciphertext (`ENCRYPT_MODE`, `WRAP_MODE`, `initSign`, `KeyPairGenerator`, `.sign(`, `.encrypt(`, `generate_private_key`, `GenerateKey(`, `createSign(`, `publicEncrypt(` and similar, in Java, Python, Go and Node), the line goes to "needs review" instead of allowed. `allowlist.write_review` counts these locations across all entries, and the verdict line shows the count. They do not change the verdict, because a key-generating line can belong to a hybrid or a bootstrap step that a person has to judge.
3. **Hybrid.** A key-exchange line (X25519, X448, ECDH, KeyAgreement, `.exchange(`) counts as the classical half of a hybrid when non-comment ML-KEM code sits in the same function, within 12 lines either way and stopping at the next function header. A line with only a curve name also needs a key-exchange marker inside that window. Lines with signature markers (ECDSA, `Signature`, `sign(`, `verify(`, RSA, Ed25519, OAEP) never count. ML-KEM that appears only in a comment never counts.
4. **Name rule.** A line in a `Legacy*.java` file, or a line whose code (comments removed) contains `legacy`, is allowed when neither it nor the three lines below it is a write path (rule 2, all languages). A `legacy` in a comment does not count. These lines are listed apart (`allowlist.legacy`, and kind `legacy-name` in `deck.json`) so that nothing leaves the count without showing up. Since evidence format 3, a line allowed by the name rule alone, with no allowlist entry, makes `r-allow` need review and fails it under `REQUIRE_REVIEW=1`, and the verdict line counts it. `prove.py` reads the lines that `residue.sh` allowed again with the same rule, so a `# legacy` comment on a Python line or a write operation on the next line does not pass `c-classic` either. Before ruleset 2 the rule looked at the whole line and only at five Java write operations, so a comment word was enough to keep a new Python or Go key out of the count, even under `REQUIRE_REVIEW=1`.
5. **Weak PQC.** ML-KEM-512 and ML-DSA-44 are never allowed, listed or not.
6. **Key size floor (ruleset 7).** A classical row whose stated size is below 112-bit security never counts as allowed, hybrid or listed: RSA, DSA, DH or ElGamal under 2048 bits, or a curve under 224 bits (P-192, `prime192v1`, `secp160`, `sect163`, brainpool 160 and 192). The NIS draft cryptographic security guideline (November 2026) allows classical public-key cryptography until 2036 only at 112-bit strength. `below_floor` in `pqlite/rules.py` reads the size from the algorithm text, which `cbom-scan.sh` fills from the line and the three below it; a row without a size is left as it was. `a-cbom` counts these locations.
7. **Exception records.** `residual_risk`, `compensating_control` and `replacement_plan` are optional entry fields for a place that cannot move yet (the NIS draft migration guidebook asks for them). They join the digest when set and stay in the evidence's copy of the list. An `exception` entry in use with one of them missing gets a warning, and `r-allow` counts the exception entries that have all three. They do not change the verdict.

**Runtime data.** `EXCLUDE="data/** *.db *.log"` and the `DATA_DIR` in `recon.json` (when it sits inside the app root) keep runtime data out of the CBOM, the counts and the weakening check. The input tree hash still covers those files. Code, config and build files (`.java`, `.py`, `.yml`, `.properties`, `Dockerfile`, `go.mod`, `package.json` and so on) are checked even when a glob matches them, so `EXCLUDE='src/**'` cannot hide classical code. Globs that would drop everything (`*`, `**`, `/`) are refused, and a run with nothing left to check is a usage error.

## Outputs

A run writes `receipt.json` (the verification evidence), `receipt.html` (the same as one self-contained page), `deck.json`, `evidence-fragment.json`, the tables under `tables/` and the raw tool output under `artifacts/`; zip inputs are unpacked under `in/`. [guide/outputs.md](guide/outputs.md) describes each file, what to open first, what to check before sharing the folder, and the fields that stay stable within an evidence format. The run, its progress lines, the settings line, the typo warnings and the console's next steps are described in [guide/quickstart.md](guide/quickstart.md) and [guide/configuration.md](guide/configuration.md).

### CycloneDX CBOM

From 0.7.0 every run also writes its CBOM rows as CycloneDX 1.6 JSON (`pqlite/cdx.py`): `tables/cbom-orig.cdx.json` and `tables/cbom-fixed.cdx.json`, or `tables/cbom.cdx.json` for `pqproof inventory`. The CSV stays the table of record. The export judges nothing: each CSV row becomes one `evidence.occurrences` entry, with its status, tool, use, threat, reason and masked note in `additionalContext`, and the component (one per asset type and name) carries the distinct values as `pqproof:status`, `pqproof:threat`, `pqproof:use` and `pqproof:alg_raw` properties. A name is normalised only when the whole algorithm text matches a known form (ML-KEM-768, ML-DSA-65, SLH-DSA-SHA2-192s, RSA-3072, EC-secp256r1, the three IANA hybrid TLS groups); anything else keeps its text, and a primitive the scanners did not establish is `unknown`. `nistQuantumSecurityLevel` comes from FIPS 203, 204 and 205 (ML-KEM 512, 768, 1024 = 1, 3, 5; ML-DSA 44, 65, 87 = 2, 3, 5; SLH-DSA 128, 192, 256 = 1, 3, 5), and is 0 for a component with a Shor-breakable row; KpqC names, families without a parameter set and hybrids get none. The file is reproducible on purpose: no timestamp, and a `serialNumber` derived from the content (UUID v5 of its SHA-256), against the CycloneDX advice of a new serial per generation, because the evidence is hashed and `--verify` recomputes it. Version 1.6 is used because the 1.7 fields (`algorithmFamily`, `ellipticCurve`) fail 1.6 validation and most consumers read 1.6. The tool does not validate the file at run time; CI downloads the official 1.6.2 schemas, checks their SHA-256 and validates with jsonschema (`tests/test_cdx.py`, `CDX_SCHEMA_DIR`). The export module is not a rule file, so the ruleset does not change.

## Verification evidence and the evidence hash

`receipt.json` is the verification evidence for one run. It holds:

- `inputs`: for each side, the absolute path, folder or zip, the zip SHA-256, the file count, the skipped folders and symbolic links (see Skipped folders) and the tree SHA-256;
- `format_version`, `tool_version`, `ruleset_version` and `ruleset_sha256` (evidence format 2, see below), and `skip_dirs` (format 3: the copied `scan/skip-dirs` and its SHA-256);
- `tools`: name, path, version and SHA-256 of `cbom-scan.sh`, the `residue.sh` copy that ran, `scan/test-paths.ere`, `prove.sh`, `prove.py` and each `pqlite/` module, the `tls_probe` source, the `tls_probe` binary when this machine has one (an absent binary is left out rather than listed with a version; from 0.2.0 its version ends in `(release)`, `(local)` or `(unchecked)`, see TLS targets), Python and OpenSSL;
- `params` (including `require_review`, and from format 3 `profile`, `fail_on_review`, `require_resolved`, `expect_from`, `review_max_age_days` and `max_file_bytes`), `changed` (added, removed and modified files), `cbom` (with `tests`), `java` (the residue counts, with `tests`), `tls`, `weakening`, `excluded`, `test_paths` (the copied list and its SHA-256);
- `allowlist`: each entry with its status, the lines it allowed, `lines_fixed`, `lines_orig` and `orig`, `reviewed_by` and `reviewed_at` (`null` when missing or not accepted), `reviewed_via` (`entry`, `top` or `null`) and `digest` (the entry's current `reviewed_digest` value), plus `unreviewed`, the number of entries in use without an accepted review, `unused`, `unused_orig_lines`, `write_review`, and `top_digest`, the current value for a pair at the top; from format 3 also `expires_at`, `approval_ref` and `expired` per entry, `expired`, `composite` (composite signature locations) and, under `cbom.*`, `unresolved`;
- `checks` and `verdict`, `timeline` (UTC start and end of each step);
- `artifacts`: every file the run wrote under `artifacts/` and `tables/`, plus `evidence-fragment.json`, with its size and SHA-256. Every field that names a file has a `*_sha256` partner.

**Tree hash.** List every regular file under the root (skipping the folders in `scan/skip-dirs` and `.DS_Store`) as `(relative path, SHA-256 of the content)`; a symlink is recorded as `symlink:<target>` and never followed. Sort the list, then hash the concatenation of `path + "\0" + digest + "\n"` with SHA-256. Formats 1 and 2 skipped a fixed list of names at any depth (`.git`, `node_modules`, `target`, `build`, `__pycache__`, `.gradle`, `.idea`, `__MACOSX`, `.venv`, `venv`); `--verify` still uses that list for them, and the `skip_dirs` copy for format 3.

**Evidence hash.** Take `receipt.json` without the `receipt_id` field and write it in RFC 8785 canonical form: object keys sorted by UTF-16 code units, no whitespace, UTF-8, numbers in ECMAScript notation. SHA-256 of those bytes is the evidence hash, stored as `receipt_id`. All keys in the file are ASCII today. Values may contain Korean text, which does not affect key order. An integer above 2^53 in absolute value has no exact double, so the tool refuses to hash it rather than give a hash other verifiers cannot reproduce. `tests/test_evidence_strict.py` checks the sort and number vectors of RFC 8785 and recomputes every receipt under `tests/golden/evidence/` with a second implementation in `sarif.py` and, when Node.js is installed, in JavaScript.

The evidence hash names one run. `receipt.json` also holds the run times (`started_at`, `finished_at`, `timeline`), the absolute input and tool paths and CBOM file names with a time stamp, so two runs on the same inputs give different evidence hashes. The verdict and the check results come out the same.


**Recheck.** `bash prove.sh --verify <folder>` (or `python3 -I -B pqlite/receipt.py verify <folder>`) checks:

1. `receipt.json` is strict JSON (UTF-8 without a byte order mark, no duplicate keys, no `NaN` or `Infinity`, nothing after the object) and byte for byte the tool's own serialization of its values, so every parser reads the same verdict; it fits the schema, and its format is one this tool reads (1 or 2);
2. `receipt_id` equals the recomputed evidence hash, and from format 2 `ruleset_sha256` equals the hash recomputed from the rule files of that ruleset in `tools`, with a `ruleset_version` that `scan/ruleset.json` gives that hash;
3. every listed file has the recorded size and SHA-256, and the folder holds no other file (apart from `receipt.json`, `receipt.html`, `deck.json`, `README.txt` from format 3, and the unpacked inputs under `in/`);
4. every `*_sha256` partner names a listed file with that hash, and the `residue` entry in `tools` has the hash of the residue copy under `artifacts/` (`java.script_sha256`);
5. for zip inputs, the unpacked tree under `in/` hashes to the recorded tree SHA-256;
6. the verdict and the check statuses agree with the numbers they come from, including `allowlist.unreviewed` against the entries, `r-allow` against that count, the unused entries and `require_review`, each entry's `lines_fixed` against its `allowed` and `review` lines and its status, `lines_orig` against `orig`, and `unused`, `unused_orig_lines` and `write_review` against the entries (an entry counts as unused when its status is `unused`, or `invalid`, `excluded` or `outside` with `lines_orig` above 0). Newer evidence, the kind with `test_paths` or `lines_fixed`, must keep `unused`, `unused_orig_lines` and `write_review`; deleting them to look like older evidence fails;
7. each allowlist entry's `reviewed_by`, `reviewed_at` and `reviewed_via` match what the copy of the allowlist under `artifacts/` gives;
8. `receipt.html`, `deck.json` and, from format 3, `README.txt` (what to open first, the re-check command and what to look at before sharing) are byte-for-byte what the evidence renders to;
9. for newer evidence, `evidence-fragment.json` and `tables/report.md` give the same verdict (and, in the fragment, the same check statuses) as `receipt.json`. `--verify` does not rebuild those two files, so editing only `receipt.json` to change the verdict shows up here.

`--verify` exits 0 when every check passes, 1 when one fails, 2 when the folder or its `receipt.json` does not exist, and 4 on an unexpected error inside the tool.

A hash shows that a file is the one the evidence describes. It does not show who produced it: anyone can change a file and write new hashes. Compare `receipt_id` with a value from a place you trust, such as the console output of the run or a submission record.

### Versions in the evidence

From evidence format 2 (0.1.0), `receipt.json` also records:

- `format_version`: 3 since 0.2.0, 2 in 0.1.x. Evidence without this field is format 1, written by the public copies before 0.1.0. Format 3 adds `skip_dirs`, hashes the input trees with the skip rules of `scan/skip-dirs` instead of the fixed list (see Tree hash), counts lines allowed by the name rule alone under `r-allow` and on the verdict line, and its note says `pqproof --verify`.
- `tool_version`: the package version, read from `src/pqproof/__init__.py`, the one place the version is set.
- `ruleset_version` and `ruleset_sha256`: which rules judged the run. Ruleset 2 is eleven files: `scan/cbom-scan.sh`, `scan/residue.sh`, `scan/test-paths.ere`, `scan/skip-dirs`, `scan/profiles.json`, `pqlite/scan.py`, `pqlite/verify.py`, `pqlite/allowlist.py`, `pqlite/rules.py`, `pqlite/skipdirs.py` and `pqlite/tlsprobe.py`. Together they hold the detection patterns, the test-path rule, the skipped folders, the algorithm profiles, the allow rules, the TLS-weakening rules, the verdict constants and the status of each check, and the TLS target verdict. Ruleset 1 was the first six without `scan/skip-dirs`. `ruleset_sha256` is the SHA-256 of one line per file, `path + "\0" + SHA-256 + "\n"`, sorted by path, over the files that actually ran. `scan/ruleset.json` lists the files of each ruleset, and `--verify` recomputes the hash from the files of the ruleset the receipt names. `scan/ruleset.json` gives each published hash a name. A run with a changed rule file, a custom `RESIDUE` or another `CBOM_SCAN` is named `<current>+modified`. From ruleset 5, `scan/ruleset.json` also keeps the hash of the rule files without comments (`comment_free`: Python comments, full-line comments and blank lines outside quotes and heredocs in the shell scanners, `#` lines in `scan/test-paths.ere` and `scan/skip-dirs`). A later edit that changes only comments is recorded as an alias of the same ruleset (`aliases`, `pqlite/version.py --alias`), so its runs keep the name; `--verify` still recomputes `ruleset_sha256` from the file hashes in `tools` and accepts the recorded hash or an alias.

`--verify` refuses a format it does not know (`format_version` above the formats it reads) and says to use a newer pqproof.

`format` is the fixed string `pqc-proof receipt 1` that the first public copy wrote. It has not changed since and does not track the format; read `format_version`.

The JSON Schemas under `schemas/` and the list of stable fields are in [guide/outputs.md](guide/outputs.md#machine-readable-contract). `tests/make_schemas.py` writes the schemas from the code, and a test fails when they drift.

### Older evidence

`--verify` keeps reading format 1. It accepts the note the first public copy wrote (it said 영수증, receipt). It rebuilds that copy's `receipt.html` and `deck.json` with the copy's own words, so the byte-for-byte page check still applies and its verdict line keeps its old text. `--verify` keeps reading format 2 (0.1.0 and 0.1.1, ruleset 1) with its own note, words, tree walk and `r-allow` rule. `tests/golden/evidence/` holds one evidence folder from each of three earlier public copies and one from 0.1.0. `tests/golden/make_fixture.py` replaced local paths in them and recomputed the hashes. The verdicts, checks and counts are as those versions wrote them. Development builds between those versions are not supported.

## TLS targets

`b-tls` measures a running server: [guide/configuration.md](guide/configuration.md#tls-targets) shows how to build the probe and pass addresses. From 0.8.0 (`tls_probe` 0.6.0) the probe verifies every target's certificate by default against the system trust store and the server name (the `@servername`; without one, the host of the address for this default and `localhost` for the other two, as before); `#/path/ca.pem` trusts only that CA, as before, and `#tofu` opts in to trust on first use, which is weaker: an unchecked handshake reads the chain and the measured handshake verifies against its last certificate. `tls.targets[].trust` records `system`, `ca-file` or `tofu`, and the probe's own `trust:` line is kept in each handshake. A handshake that fails certificate verification is never read as a refusal or a pass, because the group was not measured: the target's `why` says so, and `b-tls` is undecided. Each handshake is judged on its own, so a failure that was measured (the hybrid-only offer refused before any certificate is sent, or the old client accepted under `CLASSIC=deny` with a certificate that verifies) still fails the target, and `why` keeps both reasons. The run also stays undecided, and measures nothing, when the probe binary reports a version other than the one the code expects (`tls_probe version`), and a `connect` that ends with a usage error or a timeout is a tool error, not a handshake. In container mode the system trust store belongs to the target image, which is built from the tree under test, so the target can choose it; the probe clears `SSL_CERT_FILE` and `SSL_CERT_DIR` so the image's environment cannot point it elsewhere, the `b-tls` line names container-mode system trust, and a CA file is the way to trust only that CA. Before 0.8.0 a target without a CA was trusted on first use, so a self-signed server measured without a CA moves from pass to undecided. Before it measures a target, the probe tests itself against two local reference servers, one hybrid and one X25519-only, always with their own CA given explicitly, and the run is undecided if either control comes out wrong. On the host with OpenSSL 3.5 or later, the tool repeats the hybrid-only handshake with `openssl s_client` and compares the group; a disagreement is undecided too. From 0.8.0 that handshake also stops on a verification error (`-verify_return_error`) and checks the name (`-verify_hostname`, or `-verify_ip`), with `-CAfile` and `-partial_chain` for a CA file or the `#tofu` anchor (Go trusts any certificate in its root pool, and the anchor is often a leaf), and OpenSSL's default trust paths otherwise. It also no longer reads a handshake that `s_client` stopped on a verification error as a success (it still prints the cipher suite then). Before 0.8.0 it verified only against a CA file or the trust-on-first-use anchor and never checked the name.

The probe is a binary on the local disk, and anyone who can write to that folder could replace it with one that always reports a hybrid handshake. From 0.2.0 the release workflow puts the `SHA256SUMS` of the binaries it built into the wheel and the sdist as `pqlite/tls_probe-release.sha256`. Before a TLS run the tool hashes the binary it is about to use and records the result in `tls.probe_build` and on the `b-tls` line: `release` (the hash matches the release), `local` (it does not: built by hand or changed, a person should look) or `unchecked` (no release list, as in a source checkout). It does not change the verdict. The source tree never carries the list, so a source run says `unchecked`.

From 0.6.0 (`tls_probe` 0.5.0) each handshake also records the cipher suite and the leaf certificate's expiry (`cipher`, `cert_not_after` in RFC 3339 UTC) next to the protocol and group, in `tls.targets[]`, `tables/tls.csv` and, when present, a column of the TLS table in `receipt.html`. The NIS draft migration guidebook asks a TLS scan for these per domain. They do not change `b-tls`. The probe reports the suite it negotiated, not every suite a server accepts.

## SARIF and the GitHub Action

`pqproof sarif` turns the evidence into SARIF 2.1.0 after recomputing every hash it reads, and `action.yml` wraps a run, `--verify` and the SARIF step. The rule table, the Action inputs and outputs, and the GitHub, GitLab, Jenkins and SonarQube examples are in [guide/ci.md](guide/ci.md).

## Tests

```bash
bash prove.sh --unit                 # unit tests
bash prove.sh --selftest             # end-to-end self-test, S1 to S11 below
python3 -I tests/mutations/run_mutations.py --strict --golden tests/golden/verdicts.json
bash scan/cbom-scan.sh --selftest    # scanner assertions
```

`--unit` and `--selftest` print `n 통과 · m 건너뜀 · k 실패` (passed, skipped, failed) and name each skipped case. Without the `tls_probe` binary the TLS unit tests and self-test case S6 are skipped, and `--unit` says how to build it; the evidence tamper tests use a run without TLS and do not need it; the SARIF schema test needs `jsonschema` and a schema file in `SARIF_SCHEMA`. With `STRICT=1` any skip fails the run, which is how CI runs them. `cbom-scan.sh --selftest` has 162 assertions and prints `selftest: PASS n · FAIL m · SKIP k of t`. Four need OpenSSL 3.5 or later (an ML-DSA-65 certificate, an ML-KEM-768 key and an ML-KEM TLS server), and seven need `ssh-keygen`, `keytool` or Ed25519 support. An assertion whose tool is missing counts as skipped, never as passed, and CI reads the total from that line: four skips are allowed on Ubuntu's OpenSSL 3.0 and none on macOS. Before 0.2.0 the scanner dropped those assertions silently and CI kept the expected total in a variable. None of the tests touch the network; the TLS cases use servers on 127.0.0.1. An installed package runs the same tests with `pqproof --unit`, `pqproof --selftest` and `pqproof mutations`. The optional workflow `.github/workflows/kpqc-e2e.yml` (started by hand or by a release tag) builds real KpqC implementations: it downloads pinned KpqC reference implementations, mlkem-native and PQClean from GitHub and pq-verify from PyPI, checks their SHA-256, builds the libraries (`tests/kpqc_targets.sh`) and runs question sheet, harness and judge on them (`tests/kpqc_e2e.py`). Like the ML-KEM libraries the unit tests audit in CI, these builds belong to the tests; the tool itself never builds or runs the code it checks.

### Golden verdicts

`tests/golden/verdicts.json` keeps the verdict, the check statuses and the main counts (blocking locations, classical lines per family, ML-KEM and ML-DSA lines, weakening hits, allowlist counts) of every tree case above, including the two plain example runs. `run_mutations.py --golden tests/golden/verdicts.json` fails when any of them moves. After an intended rule change, rewrite the file with `--write-golden` and record the change under "Verdict impact" in `CHANGELOG.md`.

A different ruleset name alone (`1+modified` while rule files are being edited) fails no case. It is reported once, at the top of the golden summary, and a case fails only when its verdict, a check status or a count moves. `--diff-golden FILE` writes the moved cases and fields as a Markdown table, a draft for the verdict-impact entry. `--write-golden` prints the same comparison against the file it replaces, then writes it.

### Rule tests

`tests/test_rules.py` pins what each rule does today, one row per alternative. Every pattern alternative in `residue.sh` has a line it catches and a near miss it must not catch, along with the comment, test-path, `legacy`, `Legacy*.java`, same-line ML-KEM and write-operation cases. Every rule in `pqlite/verify.py` has a change it flags and one it does not. The allow rules in `pqlite/rules.py` are tested at their edges: an ML-KEM line 12 lines away counts as hybrid and 13 does not, a write operation 3 lines below an allowed line counts and 4 does not, and `a-input` passes at exactly half the original files in common and is undecided one file below. A rule or an alternative with no row fails the test.

`tests/code_mutants.py` plants 44 small changes in the rule code (an alternative deleted, a threshold moved, a list shortened) and runs the behaviour and sync tests on each copy. Every change must fail at least one test. A weekly workflow (`.github/workflows/code-mutants.yml`) runs it.

`tests/test_rule_sync.py` checks rule values that are copied between files: the residue rule IDs against `FAMILIES` in `pqlite/rules.py` and the rules SARIF reports, the write operations, the `legacy` word and the `Legacy*.java` name rule, and that `prove.py` and `pqproof doctor` pick the same OpenSSL. A test that pins a known gap (current behaviour that a later release fixes) lists the review item in `KNOWN_GAPS`, and `--unit` prints those numbers after the counts. Fixing the gap fails that test on purpose, so the fix also flips the expectation.

## Versioning and maintenance

- Semantic Versioning. While the version is 0.x, a change that can move a verdict (a detection pattern, the test-path list, an allow rule, a check added or removed) bumps MINOR, and so does a new command or option. From 1.0 a verdict change bumps MAJOR and a new command or option bumps MINOR. Other fixes bump PATCH, so a release that moves a verdict is never a PATCH release. `tests/version_policy.py` checks the verdict part in CI and in the release workflow, against the previous release tag; a new command or option is for the person who cuts the release to check. Options of the test tools (such as `run_mutations.py --diff-golden` in 0.1.1) do not count as options of the tool. Only the latest MINOR release gets fixes.
- The version is set once, in `src/pqproof/__init__.py`. `pyproject.toml` reads it, and so do `bash prove.sh --version`, `pqproof --version` and `receipt.json`.
- A changed rule file needs a new ruleset entry in `scan/ruleset.json`: its hash, `since` (the first version that ships it), `verdict_impact` (`yes`, or `no` when only comments or wording changed) and the hash of each rule file. `python3 pqlite/version.py --ruleset-json` prints the hashes. `tests/test_versioning.py` fails until the entry is there, and it names the rule files that changed. If verdicts moved, rewrite `tests/golden/verdicts.json` with `run_mutations.py --write-golden` and write "Verdict impact: yes" in `CHANGELOG.md`, all in the same commit. The version policy check fails when golden verdicts moved since the last release tag and the matching CHANGELOG entry (`[Unreleased]` before the release) does not say yes. `scan/ruleset.json` written in the old form (a bare hash per name) is still read.
- A change to the evidence format raises `format_version` and keeps reading the older formats. Before such a release, save evidence from the current version with `tests/golden/make_fixture.py` so that `tests/test_golden.py` keeps checking it.
- A release starts from a tag `vX.Y.Z` (`.github/workflows/release.yml`). It first runs the whole CI workflow (`ci.yml` through `workflow_call`), so a release passes every job a push does. The tag must match the version and a dated `CHANGELOG.md` entry, and the tagged commit must be on `main`. The workflow builds the four `tls_probe` binaries with `SHA256SUMS` and `BUILDINFO`, and the wheel and the sdist with build tools pinned by hash (`.github/requirements/build.txt`, no build isolation). It writes a CycloneDX SBOM of the wheel and adds the file hashes, the `tls_probe` binaries with their Go version, and the external programs the tool runs (bash, OpenSSL, keytool) to it (`.github/scripts/sbom_extend.py`), then checks it against the CycloneDX schema. Every asset, `BUILDINFO` included, gets GitHub build provenance (`gh attestation verify <file> --repo g1mn/pqproof`), and the wheel gets an SBOM attestation. Then it publishes to PyPI with Trusted Publishing.
- Workflow actions are pinned to commit SHAs, release and lint tools to versions with hashes, and Dependabot proposes updates for both. A `lint` job runs ruff (error rules only), shellcheck on the shell scripts (`scan/cbom-scan.sh` included since ruleset 2; a fix there changes the ruleset hash, so it goes with a ruleset change) and zizmor on the workflows and the Action.

## Limits

- **Rules, not proof.** A pass means the rules found nothing. Whether the rules are right, complete or fit your service is a human judgement.
- **Static detection.** Regular expressions with assignment tracking inside a file and `static final` constants across Java files, and string pieces joined with `+` (`"R" + "SA"`). An algorithm name that arrives from configuration at run time cannot be read; since 0.2.0 such a Java row needs review in `a-cbom` and shows on the verdict line (`REQUIRE_RESOLVED=1` fails it), and a "check" row that `scan.py` traced to a post-quantum name drops to "info". `EXPECT_FROM=api` counts `c-expect` from post-quantum API calls the scanners recognise (Java JCA and BouncyCastle, Node `generateKeyPair`, Go `crypto/mlkem`) instead of name lines, so a tree that keeps only the constants fails.
- **Coverage.** Java, Go, Python, Node and nginx have the most rules. Libraries whose API hides the algorithm name are matched by API: PyNaCl `nacl.public`/`nacl.signing`, tweetnacl `nacl.box`/`nacl.sign`, libsodium `crypto_box`/`crypto_kx`/`crypto_sign`, Go `x/crypto/nacl`, `curve25519` and `ed25519`, wolfSSL `wc_ecc_`/`wc_ed25519_`/`wc_Rsa*`, and Nimbus `ECKeyGenerator`, `RSAKeyGenerator`, `OctetKeyPairGenerator` and `Curve.P_256`; `pynacl`, `tweetnacl`, `libsodium-wrappers`, `@noble/curves` and the `*-dalek` crates are listed as dependency rows. Code that turns TLS 1.3 off (`MaxVersion` below TLS 1.3 in Go, `maxVersion` or `secureProtocol` in Node, `maximum_version` or `OP_NO_TLSv1_3` in Python, a Java protocol list or Spring setting without `TLSv1.3`) blocks in `a-cbom` and, when a change adds it, fails `b-weakening`. Other languages get what `cbom-scan.sh` and `residue.sh` find by name.
- **TLS.** The probe measures servers. TLS terminated outside the code (Caddy, Envoy, Traefik, a cloud load balancer) produces no signal; pass its address in `TLS_TARGETS` yourself. The tool cannot tell whether the server you measured runs this exact fixed tree.
- **Hybrid window.** The 12-line window and the function-header pattern are heuristics. If one function holds both a classical-only branch and an ML-KEM branch, the classical branch may count as hybrid. Every such line is listed in `allowlist.hybrid`.
- **Large files.** `scan.py`, the weakening check and the allowlist check skip any file over the size limit (`MAX_FILE_MIB`, default 1 MiB, recorded as `params.max_file_bytes`). Only `cbom-scan.sh` and `residue.sh` look at such a file, and code or config files over the limit are listed in `inputs.*.oversize` and make `a-input` need review. `residue.sh` reads its file list from a temporary file, so a tree with many files or long paths no longer hits the argument limit (before ruleset 2 it stopped with "Argument list too long" and `c-classic` stayed undecided).
- **Allowlist.** The allowlist changes the verdict, and the tool cannot judge a reason. It checks where an entry points, whether its lines exist, whether they write, and whether someone signed it. For real reviews run with `REQUIRE_REVIEW=1` and keep the list with a person.
- **Review fields.** The tool checks the form of `reviewed_by` and `reviewed_at` and whether `reviewed_digest` matches, not who wrote them. An agent that writes the allowlist can fill them and compute the digest too, so the review step has to stay with a person. The digest catches an entry added or changed after the review when the change is in the entry text. A change only in the code the entry points to goes unnoticed, and so does running the list against a tree it was not written for.
- **Test paths.** A path that matches the test rule counts as tests even if production code lives there. Those lines are listed, not judged. The marker protects only the `src/main/` layout. Production code in a top-level `examples/` folder counts as tests, and a test-looking folder deeper in a tree without `src/main/` (`internal/mocks/`) is scanned as code.
- **Policy data.** The tool does not read the values in JSON or YAML that pick an algorithm. Two trees that differ only in such a value get the same verdict.
- **Outside the tree.** TLS settings, certificates and services configured outside the given tree (a host's TLS configuration, for example) are out of view, so the verdict can differ from a check that tests the running service. The tool does not open files outside the tree, so the same tree gets the same verdict on every machine: a certificate path in an nginx or Apache setting that points outside the tree becomes a "check" row (인증서(트리 밖 참조)), and an SSH `HostKey` outside the tree is named from its file name. `cbom-scan.sh` run on its own reads those files with `HOST_FILES=1`; `prove.sh` never passes that setting. Before ruleset 2 the scanner read them when they were readable, so a run on a host with the files could fail where a run elsewhere passed.
- **Symbolic links.** The tool records a link and its target and never follows it. Build tools do follow links, so a link in the fixed tree whose target is outside the tree or in a skipped folder is reported in `a-input`: undecided when the link or target is code, config or a build file or has no extension (it may be a folder), needs review otherwise, and a failure under `REQUIRE_REVIEW=1`. Links in a zip are not unpacked and get the same treatment. A link to a file inside the tree is fine, because that file is checked where it is.
- **Skipped folders.** A folder named `build`, `target`, `dist` or `vendor` at the top of the tree or next to a build file is treated as build output or vendored dependencies and not checked. Code there shows up only as a count in `inputs.*.skipped` and as "needs review" in `a-input`. Production code kept in such a folder outside `src/main/` is not judged.
- **No function or performance testing.** Use your own tests for that. The implementation check (`--impl`) only compares answers that your harness produced with reference KAT versions. It does not run your code, and a match is not a conformance test or a certification (not KCMVP). The pq-verify bridge reports what pq-verify reports about your library with its pinned vectors; it is not a certification either.
- **Scale.** I have run it only on small services so far, not yet on production codebases.

## 한국어 요약

2026년 양자내성암호 전환 해커톤 본선에서 실제로 쓴 검증 도구다. 이 대회에서 대상(부총리상)을 받았다. 전환 전과 후의 소스를 넣으면 사유 없이 남은 기존 공개키 암호 코드가 없는지, NIST 보안레벨 3 이상의 ML-KEM·ML-DSA(기본은 ML-KEM-768·1024, ML-DSA-65·87)를 쓰는지, TLS 설정을 약하게 바꾸지 않았는지 보고 전환이 끝났는지 판정한다. 판정에 AI 모델을 쓰지 않으므로 입력이 같으면 판정도 같다.

- 실행: `pip install pqproof` 뒤 `pqproof <전환 전 폴더|zip> <전환 후 폴더|zip>`, 저장소에서는 `bash prove.sh <전환 전> <전환 후>`. 예제로 돌려 보려면 `bash prove.sh examples/classic examples/pqc`(휠에도 예제가 들어 있다: guide/quickstart.md). 판정에는 bash·OpenSSL 이 있어야 해서 Windows 에서는 WSL 안에서 돌리고, 증적 재검증(`pqproof --verify`)과 SARIF 변환은 파이썬만으로 Windows 에서도 된다.
- 출력: 판정(종료 코드 0 통과, 1 실패, 2 사용법·입력 오류, 3 미판정, 4 도구 오류, 5 통과지만 검토 필요(`FAIL_ON_REVIEW=1`일 때만)), 전후 CBOM 표, 검증 증적(`receipt.json`, `receipt.html`), 증적 해시. 증적 해시는 증적 JSON을 RFC 8785 방식으로 정규화해 SHA-256으로 계산한 값이다. `pqproof --verify <출력 폴더>`(저장소에서는 `bash prove.sh --verify`)로 누구든 다시 계산해 볼 수 있다. 증적에 실행 시각과 입력 폴더의 절대 경로가 들어가서, 입력이 같아도 증적 해시는 실행할 때마다 달라진다.
- 용어: 본선판 출력의 '영수증'을 '검증 증적'으로, '범주 3'을 '보안레벨 3'으로 바꿨다. 둘 다 NIST의 security category를 가리키며 영어 출력(CBOM 표의 NIST 칸)은 security category를 그대로 쓴다. 파일과 칸 이름은 `receipt.json`, `receipt_id`처럼 receipt를 그대로 쓴다.
- 사람 확인: 도구는 허용 목록의 사유가 맞는지 모르므로 사람이 읽고 항목(또는 목록 맨 위)에 `reviewed_by`(이름·계정)와 `reviewed_at`(ISO 8601 날짜·시각)을 적는다. 목록 맨 위에 적을 때는 실행할 때 찍히는 `reviewed_digest` 값도 함께 적는다. 그 뒤에 항목을 더하거나 고치면 값이 맞지 않게 되어 맨 위 칸을 물려받던 항목이 모두 확인 전으로 돌아간다. 확인 전 허용 항목이 있어도 통과와 종료 코드 0은 그대로다. 판정을 '통과(허용 n건 사람 확인 전)'으로 적을 뿐이고 `REQUIRE_REVIEW=1`을 주면 실패로 끝난다. 칸 형식이 틀리거나 값이 맞지 않으면 경고를 남기고 확인 전으로 센다. 두 칸은 `receipt.json`에 들어가 증적 해시에 반영되며 `--verify`가 증적과 함께 남긴 허용 목록 사본과 맞춰 본다.
- 경로·비밀: 출력에는 입력 폴더, 도구, 출력 폴더의 절대 경로가 적히고, zip 입력이면 in/ 에 소스 전체가, artifacts/ 의 스캐너 출력에는 소스 줄이 그대로 들어 있다. 도구가 직접 쓰는 표 발췌와 SARIF snippet 은 비밀번호·토큰처럼 보이는 값을 *** 로 가린다. 출력 폴더를 남에게 넘기기 전에 확인한다.
- 건너뛰는 폴더: `scan/skip-dirs` 한 곳에 둔다. `.git`·`node_modules`·`venv` 같은 이름은 어느 깊이든 건너뛰지만 `src/main/` 아래에서는 빌드 파일 옆일 때만 건너뛴다. `build`·`target`·`dist`·`vendor`는 트리 맨 위이거나 빌드 파일(`pom.xml`·`go.mod`·`package.json` 등) 옆일 때만 건너뛰고 `src/main/` 아래는 늘 본다. 트리 해시와 세 스캐너가 같은 목록을 쓴다. 산출물 폴더와 제자리(트리 맨 위·빌드 파일 옆)가 아닌 의존성 폴더는 파일 수와 함께 증적에 남고, 고친 판의 그런 폴더에 코드 파일이 있으면 a-input 이 검토 필요다.
- 이름 규칙: `Legacy*.java` 파일이나 주석을 뺀 코드에 `legacy`가 든 줄은 그 줄과 아래 3줄에 새 키·서명·암호화(자바·파이썬·Go·Node)가 없을 때만 허용한다. 주석의 `legacy`는 세지 않는다. 허용 목록 항목 없이 이름 규칙으로만 허용한 줄이 있으면 r-allow 가 검토 필요이고 `REQUIRE_REVIEW=1`이면 실패다.
- 구현 검증: `pqproof impl prompt|judge`는 KpqC 구현(SMAUG-T·NTRU+·HAETAE·AIMer)의 답안을 고정한 참조판 KAT 와 대조한다(검사 i-kpqc). PQ-Proof 는 구현을 빌드하거나 실행하지 않고, 결과는 '참조판 X의 KAT와 일치'이지 표준 준수 시험이나 공인 시험(KCMVP)이 아니다. `--pq-verify "--audit-kem <라이브러리> ML-KEM-768"`을 주면 사용자가 따로 설치한 pq-verify 로 NIST PQC 라이브러리 감사도 해서 같은 증적에 담는다(검사 i-nist). 이때 라이브러리를 불러 실행하는 것은 pq-verify 이고 샌드박스가 아니므로 믿지 못할 라이브러리는 컨테이너나 VM 안에서 돌린다. 네트워크 옵션(`--live`)과 출력 경로 옵션은 받지 않고, 종료 0·VERIFIED·범위 완전이면 통과, 통과 못 한 단계가 있으면 실패, 그 밖은 미판정이다. 흐름, 판정 표, 한계, 판 목록 갱신 절차는 [guide/impl.md](guide/impl.md)에 있다.
- 한 트리: `pqproof check <폴더|zip>`은 원본 없이 지금 상태만 판정한다(전환 뒤 회귀 방지). 두 트리를 대조하는 검사는 '해당 없음'이다. `pqproof inventory <폴더|zip>`은 판정 없이 CBOM과 계열별 고전 줄을 센다(첫 현황 조사).
- 허용 목록의 `expires_at`(만료일)이 지나면 r-allow 가 검토 필요(`REQUIRE_REVIEW=1`이면 실패)이고, `approval_ref`(결재 번호)는 증적에 남는다. 모르는 칸은 경고한다.
- 알고리즘 프로필(`PROFILE`, `scan/profiles.json`): 기본 `nist-cat3` 는 ML-KEM-768·1024 와 ML-DSA-65·87 을 c-expect 에 센다. `cnsa2` 는 ML-KEM-1024·ML-DSA-87 만 세고 TLS 대상에 SecP384r1MLKEM1024 를 홀로 제시한다. `kpqc` 는 국내 KpqC(SMAUG-T·NTRU+·HAETAE·AIMer, NIST 비승인)도 센다. 프로필은 고전 줄을 통과시키지 않는다.
- TLS 대상 신뢰(0.8.0부터): CA 를 주지 않은 대상은 시스템 신뢰 저장소와 호스트 이름으로 인증서를 검증한다. `#/절대경로/ca.pem` 은 그 CA 만 믿고, 처음 본 인증서를 믿는 방식(TOFU)은 더 약해서 `#tofu` 를 붙여 명시할 때만 쓴다. 증적 `trust` 칸은 `system`·`ca-file`·`tofu` 다. 인증서 검증이 실패한 핸드셰이크는 협상을 재지 못한 것이라 통과도 거부도 아니다. 판정은 핸드셰이크마다 따로 해서, 재지 못한 것만 있으면 b-tls 가 미판정이고, 같은 대상의 다른 핸드셰이크나 다른 대상에서 잰 실패가 있으면 실패다.
- 복합 서명(ML-DSA-65·87 과 RSA·ECDSA·Ed25519·Ed448 을 한 키로 묶은 것)은 막지도 그냥 넘기지도 않고 a-cbom·c-classic 모두 검토 필요로 둔다. 판정 줄에 수가 나온다.
- 트리 밖: 트리 밖 파일은 열지 않는다. 설정이 가리키는 트리 밖 인증서는 '확인' 행으로만 남고, 트리 밖을 가리키는 심볼릭 링크가 코드·폴더면 a-input 이 미판정(`REQUIRE_REVIEW=1`이면 실패)이다. 그래서 같은 트리는 어느 기계에서나 같은 판정을 받는다.
- 한계: 통과는 이 규칙으로 찾은 것이 없다는 뜻일 뿐, 규칙이 옳다는 보장은 아니다. 기능과 성능은 보지 않는다. 허용 목록은 판정을 바꾼다. 사유가 맞는지는 도구가 모르니 사람이 확인해야 하고 실무 검토에서는 `REQUIRE_REVIEW=1`로 돌리기를 권한다. JSON·YAML 설정 값이 고르는 알고리즘은 보지 않는다. 넣은 소스 밖의 설정(호스트의 TLS 설정 등)도 못 보므로 판정이 실행 중인 서비스를 직접 시험한 결과와 다를 수 있다. 작은 서비스에서만 써 봤고 실서비스 규모로는 아직 검증하지 않았다.
- 공개하면서 대회 문제와 관련된 내용, 개인 경로, 대회용 보고서 표를 뺐다. 참가자가 만든 도구이며 주최·주관기관이 검토하거나 보증하지 않았다.
- 건너뛴 검사는 통과로 세지 않는다. 돌지 못한 검사는 이름과 함께 '해당 없음'이나 '미판정'으로 남고, 판정 뒤에 상태별 개수를 따로 찍는다. 단위·셀프 시험도 '통과 n · 건너뜀 m'으로 세며 `STRICT=1`이면 건너뛴 것이 있을 때 실패한다.
- 버전: 도구 버전은 `src/pqproof/__init__.py` 한 곳에서 정한다. 증적에 도구 버전, 규칙 묶음 이름과 해시(스캐너 패턴·시험 경로·건너뛰는 폴더·알고리즘 프로필·허용·약화 규칙과 판정 상수·검사 판정식 파일, 묶음 3은 KpqC 참조판 KAT 목록·발췌와 구현 검증 모듈까지 열넷), 증적 형식을 남기고 `--verify`가 규칙 묶음 해시를 다시 계산한다. 이전 공개본이 쓴 옛 증적도 계속 읽는다. 판정이 바뀔 수 있는 변경과 새 명령·옵션은 0.x 동안 MINOR로, 그 밖 고침은 PATCH로 올린다. 판정이 바뀌는 릴리스는 PATCH가 될 수 없고 CI와 릴리스 작업이 앞 릴리스 태그와 대조해 막는다(`tests/version_policy.py`). 바뀐 내용은 CHANGELOG.md의 '판정 영향' 칸에 적는다.
- 문서: 설치·설정·결과 읽기는 [guide/](guide/), 규칙과 증적 형식은 이 파일, 본선에서 쓴 이야기와 본선 뒤 바뀐 점은 [HISTORY.md](HISTORY.md)에 있다.
